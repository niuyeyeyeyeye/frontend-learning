## 二、核心概念 1：重渲染只会因为 4 种原因发生

| # | 原因 |
|---|---|
| ① | 它自己的 state 变了 |
| ② | **它的父组件重渲染了**（且它没被 `memo` 拦住）|
| ③ | 它读的 Context 值变了 |
| ④ | 它订阅的 store 切片变了（Zustand）|

除此之外什么都不会让它重渲染。

> 第 ② 条就是你在 Day6 亲手发现的那个问题：**父组件一渲染，子组件就跟着渲染**。

---

## 三、核心概念 2：`memo` 的三种失效方式（今天最实用）

```tsx
const Child = memo(function Child({ config, onPick }) { ... })
```

| props 长什么样 | memo 效果 |
|---|---|
| `config={stableObject}`（`useMemo` / `useRef` 稳住） | ✅ 跳过渲染 |
| `config={{ role: 'admin' }}`（内联对象） | ❌ **白包了**，每次都是新对象 |
| `onPick={() => {}}`（内联函数） | ❌ **白包了**，每次都是新函数 |

**结论**：`memo` 需要 props 稳定，而 props 稳定需要 `useMemo` / `useCallback`。
这就是后两个 hook 存在的**唯一理由** —— 不是为了“让函数快一点”。

---

## 四、核心概念 3：`useMemo` 的两个真实作用 + 代价

| 作用 | 什么时候用 |
|---|---|
| ① 缓存**昂贵计算**（几十毫秒那种） | 大数组过滤/排序、复杂派生数据 |
| ② 稳住**引用**（对象/数组） | 传给 memo 子组件、Context 的 value |

### 代价

- 每次渲染都要**比较依赖**（虽然很快，但不是零）
- 占一块**缓存内存**
- **依赖写错就出 bug**，而且分两种相反的失败：

| 写错方式 | 后果 |
|---|---|
| **漏写依赖** | 结果**错**（stale 闭包，永远算第一次的值）← 难查 |
| **依赖不稳定**（塞内联对象） | 结果对，但**白算了**（等于没写）← 看不出来 |

### ⭐ 加之前先问三句

1. **它省下了什么？**（一次 30ms 的计算？还是让下游 memo 能跳过？）
2. **加它本身要花多少？**（0.01ms 的计算加 useMemo 是负优化）
3. **会不会让代码更难懂？**（依赖数组是"隐藏的约束"）

**答不出第 1 句就别加。** 面试官也会这么问。

## 五、⭐ 核心概念 4：最有效的优化是「把 state 往下挪」

| 写法 | 结果 |
|---|---|
| ❌ state 在顶层，列表在它下面 | 打字 → **整个列表重渲染** |
| ✅ state 挪进输入框组件 | 打字 → 列表**完全不动** |
| ✅ state 在外壳里，列表用 `children` 传进去 | 外壳渲染，列表**不动** |

### `children` 技巧的关键（比想象中微妙）

> 关键不是"state 在第几层"，而是 **"创建 element 的那一层有没有重渲染"**。

```tsx
// ❌ 技巧失效：children 是"持有 state 的那层"创建的
function Outer() {
  const [kw, setKw] = useState('')
  return <Shell><HeavyList /></Shell>     // kw 变 → 新 element → 照样重渲染
}

// ✅ 技巧生效：children 是"永不重渲染的外层"创建的
function Outer() {
  return <Shell><HeavyList /></Shell>     // Outer 没 state，element 引用永远不变
}
function Shell({ children }) {
  const [kw, setKw] = useState('')        // state 在外壳里
  return <div><input ... />{children}</div>
}
```

> 这个坑我自己都写错过一次（第一版把 state 放在了 Outer），靠渲染计数器才发现。

## 六、核心概念 5：懒加载（唯一能治"首屏慢"的手段）

```tsx
const Chart = lazy(() => import('./Chart'))

<Suspense fallback={<div>加载中…</div>}>
  <Chart />
</Suspense>
```

**三种优化各治一种病，别用错：**

| 症状 | 用什么 | 用错了会怎样 |
|---|---|---|
| 首屏加载慢（白屏久） | **懒加载 / 代码分割** | memo/useMemo 完全无效 |
| 交互卡（打字、点击延迟） | 挪 state / 拆组件 / memo | 懒加载无效 |
| 长列表滚动卡 | 虚拟列表 | memo 只能缓解 |

### 最高收益的用法：路由级懒加载

```tsx
const Day9Layout = lazy(() => import('./day9/Layout'))
// 然后在根布局 <Outlet /> 外面包一层 <Suspense>
```

## 十、FAQ

| 现象 | 原因 |
|---|---|
| 计数器数字一开始就是 2 | StrictMode 在 dev 下把首次渲染跑两遍，生产不会 |
| 加了 memo 还是重渲染 | props 里有内联对象/函数（本页实验 2 的第 3、4 个） |
| 加了 useMemo 结果不对 | 漏写依赖（stale 闭包）—— 看 `01` 的第三个实验 |
| 用了 children 技巧但没用 | children 是"持有 state 的那层"创建的（见第五节） |
| `lazy` 组件报错 | 忘了包 `<Suspense>`，或者被懒加载的组件和 `lazy()` 写在同一个文件里 |

| 测什么 | 结果 |
|---|---|
| 父组件 tick +1 ×2 | 普通子 `1 → 3` ✅（+2）／memo 子 `1 → 1` ✅（不动） |

| 漏写依赖 | count 已是 1，而 useMemo 仍算出「count 是 0」✅（stale 闭包） |
| state 位置 | A 列表 `1→2` ✅（涨）／B 列表 `1→1` ✅（不动）／C：Shell `1→2` 但列表 `1→1` ✅（children 技巧生效） |

> 说明：**我在写这一页时把 children 技巧的第一版写错了**（state 放在了创建 children 的那一层），
