## 二、核心概念 1：数据往下走，事件往上走

React 的数据流是**单向**的（父 → 子）。所以"往上"只能靠**函数**：

| 方向 | 手段 | 一句话 |
|---|---|---|
| 父 → 子 | `props` 传数据 | 我给你看 |
| 子 → 父 | `props` 传**函数**，子调用它 | 我请求你改 |
| 兄弟之间 | **状态提升**：state 挪到最近的公共父组件 | 你俩的事，我管 |

### ⭐ 一句话原则：谁拥有 state，谁才有权改它

```tsx
// ❌ 子组件拿不到 setKeyword，也不该拿到
// ✅ 父给的是 onChange，子只是"请求父去改"
<SearchInput keyword={keyword} onChange={setKeyword} />
```

这条叫**单一数据源**。以后你查"数据为什么没更新"，第一件事就是问：
**这个 state 到底住在哪个组件里？有几个组件在改它？**

## 三、核心概念 2：Context 三件套

```tsx
const ThemeContext = createContext<ThemeContextValue | null>(null)   // ① 造管道

<ThemeContext.Provider value={value}>…</ThemeContext.Provider>       // ② 上方注入

const ctx = useContext(ThemeContext)                                 // ③ 任意深度取
```

**解决的就是 props 钻地**：`01-组件通信基础.tsx` 里 theme 要穿过 3 层才到 Level3，
中间两层完全不用它，却必须接住再传 —— 层级一深就是灾难。

### ⭐ 必学的两个习惯

**习惯 1：把 `useContext` 包成自定义 hook，并让它报错**

```tsx
function useTheme(): ThemeContextValue {
  const ctx = useContext(ThemeContext)
  if (ctx === null) throw new Error('useTheme 必须在 <ThemeProvider> 内部使用')
  return ctx
}
```

好处三条：
1. 组件里只写 `useTheme()`，不关心 Context 对象叫什么
2. 忘包 Provider 时，报的是**人话**，不是 `Cannot read property 'theme' of null`
3. 以后想换 Zustand，只改这一个 hook，所有调用方一行不动

**习惯 2：`value` 必须是稳定引用**

```tsx
// ❌ 每次渲染都是新对象 → 所有消费者重新渲染
<Ctx.Provider value={{ theme, toggleTheme }}>

// ✅ 只有 theme 变才换
const value = useMemo(() => ({ theme, toggleTheme }), [theme])
<Ctx.Provider value={value}>
```

`02-Context入门.tsx` 的第 2 个例子里有对照实验：点"tick +1"（跟 context 无关），
**没 useMemo 的那个消费者会跟着白渲染** —— 看控制台日志。

## 七、一个必须想清楚的问题：Context 是不是"状态管理"？

**不是。** 它只是一个**传值管道**，本身不存任何东西 —— state 还在 Provider 的 `useState` 里。

所以面试官问"Context 和 Redux/Zustand 的区别"，正确的答法不是"一个是内置的一个是库"，
而是：

| | Context | Zustand / Redux |
|---|---|---|
| 本质 | 传值管道（解决"传得烦"） | 独立的状态容器（解决"放哪、怎么改"） |
| 订阅粒度 | 值一变，**所有**消费者全渲染 | 可以选择性订阅，只有用到的那部分变才渲染 |
| 适合 | 低频值：主题、登录用户、语言 | 高频/复杂：列表、表单、实时数据 |
| 代价 | 层级一多容易"上帝对象" | 多一个依赖，多一层心智模型 |

**判断口诀**：这个东西变一下，会不会让一大片组件白渲染？
- 会 → 别用 Context（或拆小 Context）
- 不会 → Context 最省事

> 顺带说一句面试加分点：Context 还有一个隐性缺点 —— **依赖关系被藏起来了**。
> 看一个组件代码，你不知道它依赖哪个 Provider；把它复制到别处，运行时才炸。
> 这也是为什么 `useTheme` 里那个 `throw` 很重要。
