## 三、核心概念 1：状态住在 React 之外

Day6 你已经知道 Context 怎么共享状态了。今天先看**它的三个痛点**：

| 痛点 | 表现 |
|---|---|
| Provider 地狱 | 想在深层用，就得把 Provider 提到最外层 |
| 状态跟着组件走 | Provider 在哪个组件里，状态就在那儿；组件卸载 → 状态消失 |
| 一变就全变 | value 里任一字段变，所有消费者全部重渲染 |

**Zustand 的解法只有一句话：把状态放到模块级，组件去"订阅"它。**

```ts
// 这个 create 在模块作用域执行，不属于任何组件
export const useCounter = create((set) => ({
  count: 0,
  inc: () => set((s) => ({ count: s.count + 1 })),
}))
```

后果：

- 不需要 Provider（任何文件 `import` 就能用）
- 组件卸载了 store 还在 → **切路由、换页面数据都不丢**
- 组件订阅多少就渲染多少 → 能只订一个字段

### 动手验（30 秒，这一页最重要）

打开 `/day8`，把左边「Context 版」和右边「Zustand 版」各点 3 下，
然后点「1. 基础用法」切走，再点回来：

这就是 Day7 学的"切路由 = 卸载 + 挂载"的直接后果。

## 四、核心概念 2：`create` / `set` / `get`

```ts
type Store = { count: number; inc: () => void }

const useCounter = create<Store>()((set, get) => ({   // ⚠️ TS 下是两对括号
  count: 0,
  inc: () => set((s) => ({ count: s.count + 1 })),    // 函数式 set
  reset: () => set({ count: 0 }),                     // 合并式 set
  addBy: (n) => set({ count: get().count + n }),      // 用 get() 读当前值
}))
```

**三条要记住的写法：**

1. `create<T>()(...)` —— TS 下必须写第二个括号（`()`），少了会报错
2. 改状态用**函数式**：`set((s) => ({ count: s.count + 1 }))`。
   直接 `set({ count: count + 1 })` 容易拿到组件里那个旧的 `count`
3. **只写要改的字段**：`set({ count: 0 })`，zustand 自动保留其他字段
   （不用像 useReducer 那样手写 `{...state, count: 0}`）

### 和 useState 对照

| 要做的事 | useState | Zustand |
|---|---|---|
| 定义 | `const [n, setN] = useState(0)` | `create((set) => ({ n: 0 }))` |
| 读 | `n` | `useStore((s) => s.n)` |
| 改 | `setN(n + 1)` | `set((s) => ({ n: s.n + 1 }))` |
| 在别的组件用 | 靠 props / Context | `import` 就能用 |
| **在组件外读** | 做不到 | `useStore.getState().n` ✅ |

**最后一行是重点**：定时器、事件回调里读最新值，用 `getState()` 就不会撞上 Day4 那个闭包陷阱。

## 五、核心概念 3：选择性订阅（今天最值钱的一节）

```ts
const count = useShop((s) => s.count)   // 只订 count：别的字段变，它不渲染
```

原理（我翻了 `node_modules/zustand/react.js` 确认）：

```js
const slice = React.useSyncExternalStore(
  api.subscribe,
  () => selector(api.getState()),   // ← 拿 selector 的返回值
  ...
)
```

React 会用 **`Object.is`** 比较这次和上次的返回值：相等 → 不渲染；不等 → 渲染。
你返回一个数字，比的就是数字。**所以订阅范围 = selector 的范围。**

### ⚠️ 最容易踩的坑：selector 返回新对象

```ts
// ❌ 每次都新建对象 → Object.is 永远 false → 每次 store 变都重渲染
const { count, text } = useShop((s) => ({ count: s.count, text: s.text }))

// ✅ 办法一：分开订（最直观）
const count = useShop((s) => s.count)
const text  = useShop((s) => s.text)

// ✅ 办法二：要一次拿多个，用 useShallow
const { count, text } = useShop(useShallow((s) => ({ count: s.count, text: s.text })))
```

`useShallow` 的原理：用 `useRef` 记住上次结果，浅比较相等时**返回上一次的同一个引用**，
React 一比较引用没变，就不渲染。

> 控制台报 `getSnapshot should be cached to avoid an infinite loop` 就是这个原因。
> 所以我在 `02` 里把错误写法**只放在注释里**，没接进页面 —— 接进去页面会崩。

## 六、核心概念 4：`persist` 持久化

```ts
export const useTodoStore = create<TodoStore>()(
  persist(
    (set) => ({ ... }),
    {
      name: 'day8-todos',                              // localStorage 的 key
      storage: createJSONStorage(() => localStorage),
      partialize: (s) => ({ todos: s.todos, nextId: s.nextId }),  // 只存数据，不存函数
    },
  ),
)
```

三个细节：

| 点 | 说明 |
|---|---|
| `partialize` | 只挑要存的部分。函数不能序列化，必须排除 |
| 别放敏感信息 | localStorage 用户随时能改、任何脚本都能读 |
| **会记住旧数据** | 改了 store 结构后，浏览器里的老 JSON 还在 → 出现"字段是 undefined"的怪 bug。排查第一步：清 localStorage |

> 我加了 SSR 保护：`typeof window === 'undefined' ? noopStorage : localStorage`。
> 不加的话，服务端渲染 / 测试环境没有 `localStorage`，直接报错。

## 十、FAQ：今天可能撞上的 3 个报错

| 现象 | 原因 | 修 |
|---|---|---|
| `getSnapshot should be cached to avoid an infinite loop` | selector 返回了新对象/新数组 | 分开订，或 `useShallow` |
| 页面白屏 + `Invalid hook call` / `Cannot read properties of undefined` | 在**函数组件外**调了 `useStore()` | 组件外用 `useStore.getState()` |
| 改了 store 字段，浏览器里还是老数据 | `persist` 存着旧 JSON | F12 → Application → Local Storage → 删掉 `day8-todos` |
