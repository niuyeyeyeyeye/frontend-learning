```
├── 00-环境搭建.md          ← 本文件
├── 笔记.md                ← 阶段笔记（Day1 / Day2 …）

│   ├── 练习.ts            ← 你要改的（改到 npm run check 无报错）
│   └── 报错示例.ts         ← 故意报错，用来看真实报错（已被 tsconfig 排除）
└── day2-对象建模/
    ├── 讲解.ts
    ├── 练习.ts
    └── 报错示例.ts
```

**为什么这样分？**

- **一个项目、一份 `node_modules`**：所有 day 共用同一套 TS 环境和配置（不用每个文件夹装一遍 29MB）
- **按天分文件夹**：找文件、复习某一天都方便
- **`报错示例.ts` 被 `tsconfig.json` 的 `exclude` 排除**：它是故意写错的，不能影响 `npm run check` 的结果
- 每个 `.ts` 文件末尾都有 `export {}` —— 这让文件成为**独立模块**（各有各的作用域），
  所以分文件夹、甚至两个文件里写同名 `interface` 都不会冲突

## 一、最关键的一个认知：TS 不能直接运行

```
你写的 .ts 文件  →  tsc 编译  →  .js 文件  →  node / 浏览器 才能跑
```

- **浏览器和 Node 只认 JavaScript**，不认识 TypeScript
- TS 是"开发时"的工具：它的价值在于**写代码时就告诉你哪里错了**，以及**编辑器里的自动补全**
- 所以你的日常是两个命令：① 检查类型（不生成文件）② 编译（生成 js 再运行）

## 二、今天要用的命令（在这个文件夹里敲）

### ⚠️ 先搞清楚：npm / npx / npm run 是三回事（最容易卡住的坑）

| 命令 | 它的作用 | 什么时候用 |
|---|---|---|
| **`npm <子命令>`** | 包管理器，子命令是**固定的几十个**：`install` / `run` / `test` / `publish` … | 装包、升级、发布 |
| **`npx <工具名>`** | **执行一个可执行程序**（先去 `node_modules\.bin\` 找，找不到才临时下载） | 跑工具：`tsc`、`vite`、各种 CLI |
| **`npm run <脚本名>`** | 执行 `package.json` 里 `scripts` 中**你自己定义的**脚本 | 跑项目里配好的任务 |

**所以 `npm tsc ...` 为什么报 `Unknown command: "tsc"`？**
因为 `npm` 在找一个**叫 tsc 的 npm 子命令**——而 npm 根本没有这个子命令（只有 install / run / …）。
**它不会去找 tsc 这个工具。** tsc 是"工具"，要用 `npx` 或 `npm run` 启动。

**三种正确写法（都实测可用）**

```powershell
# ① 最省事：跑项目里配好的脚本（等价于 tsc --noEmit）
npm run check

# ② 跑单个文件（注意是 npx，不是 npm）
npx tsc --ignoreConfig --strict --noEmit day1-基础类型与推断\报错示例.ts

# ③ 最底层、一定管用（直接调用安装好的文件）
node node_modules\typescript\bin\tsc --version
```

**另外两种常见错法**

| 错误写法 | 报错 | 原因 |
|---|---|---|
| `npm tsc ...` | `Unknown command: "tsc"` | npm 没有 tsc 这个子命令 |
| `npm run tsc` | `Missing script: "tsc"` | 我们的 `package.json` 只定义了 `check` / `build` / `watch` |

**记忆口诀**

```
npm run <脚本名>   →  跑「我自己定义的任务」（脚本名要先写在 package.json 里）
npx <工具名>       →  跑「一个工具」（tsc / vite / 各种 CLI）
npm <子命令>       →  管理包（install / update / publish）
```

> 学 React 时会天天用到：`npm run dev`、`npx vite`、`npm install axios`。
> 今天把这三种搞清楚，后面能少踩很多坑。

### 具体命令

先进入文件夹：

```powershell
cd D:\前端学习\第三阶段-TypeScript
```

然后：

| 命令 | 作用 | 什么时候用 |
|---|---|---|
| `npx tsc --version` | 看版本 | 确认环境正常 |
| **`npm run check`** | **只检查类型，不生成文件** | **最常用**——改完代码就敲它 |
| `npm run build` | 编译到 `dist/` 目录 | 想真正跑代码时 |
| `node dist\day1-基础类型与推断\讲解.js` | 运行编译后的 JS | 看运行结果 |
| `npm run watch` | 监听文件变化自动编译 | 写得多的时候（可选） |

> **今天的成功标准**：`npm run check` **没有任何输出**（没输出 = 没错误 = 练习全对）。

### ⚠️ 两个会让你困惑的地方，先说明白

**① 练习没做完之前，`check` 和 `build` 都会报那 6 个错 —— 这是设计好的。**
`day1-基础类型与推断\练习.ts` 里就是我故意留的 6 个类型错误，你改完了它们才会消失。

**② 报错不影响生成 JS。** `npm run build` 即使报错，也会把 `dist\day1-基础类型与推断\讲解.js` 生成出来，
所以你想先看演示的输出，可以直接：

```powershell
npm run build          # 会报 6 个错，别慌
node dist\day1-基础类型与推断\讲解.js   # 照样能跑 ✅
```

**③ 单独检查某个文件时，TS 7 必须加 `--ignoreConfig`**：

```powershell
npx tsc --ignoreConfig --strict --noEmit day1-基础类型与推断\报错示例.ts
```

> 不加会报 `TS5112: tsconfig.json is present but will not be loaded if files are specified on commandline`。
> 记住这条的意义在于：**TS 的报错信息会直接告诉你该怎么修**——以后遇到没见过的报错，先读它。

## 四、怎么看 TS 的报错（比 JS 好读得多）

TS 报错长这样：

```
day1-基础类型与推断\练习.ts:12:3 - error TS7006: Parameter 'name' implicitly has an 'any' type.

12   function greet(name) {
                       ~~~~
```

**逐段读法**：
- `day1-基础类型与推断\练习.ts:12:3` → **哪个文件的第 12 行第 3 列**
- `error TS7006` → 错误码（搜 `TS7006` 能查到详细说明）
- `Parameter 'name' implicitly has an 'any' type` → 人话："参数 name 隐式地是 any 类型"
- 下面的 `~~~~` → 精确指出哪一段有问题

**修 bug 的顺序**：永远只看**第一条错误**，改完再重新跑（这一点和你上次修待办列表时学到的一样）。

## 五、这个文件夹是怎么装好的（你可以自己复现）

我执行了两条命令（你在自己的终端里也能跑）：

```powershell
npm install typescript --save-dev
# 或者全局安装（装一次，所有文件夹都能用 tsc）
npm i -g typescript
```

装完之后：
- `package.json` 里多了 `devDependencies`（记录依赖版本，别人拿到你的项目 `npm install` 就能装好）
- `node_modules/` 里是真实的包文件（**这个目录不要提交到 GitHub**，写进 `.gitignore`）

> ✅ **这件事我已经帮你做了**：根目录的 `.gitignore` 已创建，里面有 `node_modules/` 和 `dist/`。
> 为什么必须做：这个文件夹的 `node_modules` 有 **29.4 MB**，不忽略的话 `git add .`
> 会把几万个依赖文件提交上去（这是新手最常见的灾难）。
> **以后每建一个新项目，第一件事就是确认 `.gitignore` 里有 `node_modules/`。**
